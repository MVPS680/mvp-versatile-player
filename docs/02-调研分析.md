## 2. 生态现状：Windows 桌面缺的到底是什么

| 观察 | 说明 |
|---|---|
| 系统自带播放能力在退化 | Windows 自带的播放应用对容器格式、编码格式和外挂字幕的支持有限，很多素材直接提示"无法播放"或要求去应用商店装扩展；对 HDR、多字幕轨几乎没有处理 |
| 第三方播放器两极分化 | 一类是"功能极其丰富但很重"（设置项成百上千、界面偏工程化）；一类是"轻量但只做一件事"（只放视频，不管图片、不管系统集成） |
| 面向中文用户的细节长期被忽略 | 外挂字幕的 GBK 编码、`.zh/.chs/.cht` 语言后缀、文件名里的中文序号排序，这些在国内素材里是**常态**，但很少被当作核心能力来做 |
| 装机环境有硬约束 | 办公电脑、机房、单位统一装机常无管理员权限，需要提权才能设置"默认打开方式"的播放器直接出局 |
| 用户开始在意"安静的软件" | 广告弹窗、捆绑安装、后台联网、开机自启成为负面清单；"不打扰"本身就是竞争力 |

**结论**：市场并不缺"能放视频的软件"，缺的是**"在 Windows 上像默认播放器一样顺手、而且不打扰用户"的那一个**。

## 3. 竞品分析

### 3.1 逐个看

| 竞品 | 定位 | 优势 | 短板 / 用户的抱怨点 | 我们学什么 / 怎么避开 |
|---|---|---|---|---|
| **VLC media player** | 跨平台开源全能播放器 | 格式兼容性极强、跨平台、开源免费、口碑好 | 界面风格偏工程化、设置项繁多；中文外挂字幕的编码与语言后缀体验一般；启动与首帧偏慢；与 Windows 系统的整合（打开方式、右键菜单）需要用户自己折腾 | 学它的"格式不挑"；避开它的"重"与"界面不友好" |
| **PotPlayer** | Windows 上功能极全的播放器 | 播放能力顶尖、画质调节选项极其丰富、硬件解码支持好 | 设置项数量庞大，新用户容易被淹没；界面与交互细节偏"老派"；多数用户只用到其中一小部分 | 学它"能放的都能放"；避开它"默认设置就把人劝退" |
| **MPC-HC / MPC-BE** | 轻量、经典 Windows 播放器 | 体积小、启动快、播放内核扎实 | 界面与交互长期停留在上一代观感；中文外挂字幕编码、语言后缀这些细节不关注；功能偏"能用"而非"顺手" | 学它的"轻快"；把它缺少的"中文友好"做成我们的差异点 |
| **mpv** | 极简内核、脚本党最爱 | 画质与性能优秀、可脚本化、社区活跃 | 默认几乎是"黑窗口 + 键盘操作"，普通用户无法直接使用；需要自己写配置；图形界面是可选外壳 | 学它的"内核干净"；把"开箱即用"做足 |
| **Windows 自带播放应用** | 系统默认 | 不用装、随系统升级 | 格式支持有限、外挂字幕与多音轨支持弱、HDR 与杜比视界基本不处理 | 学它的"零安装"；在格式、字幕、系统集成上补齐 |
| **已停止维护的老牌国民播放器** | 早期装机量大 | 曾经的知名度 | 长期不更新、对新格式与新硬件解码支持落后、捆绑与广告败坏口碑 | 说明"持续维护 + 不打扰"是竞争力 |
| **IINA（macOS）** | macOS 上的现代播放器 | 界面现代、与系统深度整合、体验优秀 | 仅 macOS 可用，Windows 用户用不到 | 它证明了"现代界面 + 系统深度整合"这条路是对的，我们的方向一致 |

## 4. 用户痛点 → 我们的对策

| # | 痛点（用户原话式的描述） | 现有工具的表现 | 我们的做法 | 可验证的功能点 |
|---|---|---|---|---|
| 1 | "字幕是一堆乱码" | 部分工具不识别 GBK，要用户手动转码 | 自动识别 6 种常见编码，含 GBK / Big5 | 字幕编码解析测试（含 GBK 中文用例） |
| 2 | "字幕文件明明在旁边，它就是不去用" | 需要手动挂载；语言后缀不识别 | 同目录同名字幕自动加载，优先匹配 `.zh/.chs/.cht` | 字幕加载测试 + 设置项"外部/内嵌优先" |
| 3 | "剧集顺序全乱" | 按字符排序，"第10集"排到"第2集"前面 | 自然排序 | 播放列表排序测试 |
| 4 | "拖了进度条就黑屏/卡住" | 蓝光式时间轴与索引缺失的场景处理不好 | 跳转换算容器时间、无索引容器安全二分查找、陈旧信号丢弃 | 端到端跳转测试 + 专门的边界素材 |
| 5 | "HDR 片子整幅发灰" | 直接按普通色彩显示 | 识别 HDR 元数据并做色调映射，可关闭 | 信息面板"动态范围"一行；HDR 测试（可选素材） |
| 6 | "装了播放器却没法设为默认打开方式" | 需要管理员权限 | 只写当前用户区，免提权；一键注册/一键取消、零残留 | 真实注册表注册/注销测试 |
| 7 | "装个播放器被塞了一堆东西" | 捆绑、广告、开机自启 | 无广告、无上报、不自动启动、专注播放 | 无遥测代码；绿色目录分发 |
| 8 | "设置项太多，看不懂" | 上百个选项平铺 | 默认值即推荐值；常用项放在设置首页；不支持的场景直接说明原因 | 设置项与默认值评审 |
| 9 | "截图、逐帧、变速要开三个软件" | 功能分散 | 截图 / 逐帧 / 保持音高的变速都在同一个界面里 | 端到端截图测试、界面行为测试 |
| 10 | "打开一张 8000 万像素的照片，风扇狂转" | 直接按原尺寸上屏 | 超过上限自动缩小、避免重复上传未变化的画面、窗口最小化时不处理画面 | 图片像素上限检查 + 相关测试 |
| 11 | "手机拍的照片是躺着的" | 忽略 EXIF 方向 | 按 EXIF 方向自动旋转 | EXIF 方向测试 |
| 12 | "关个窗口要等半天" | 关闭时还在清理缓存、等设备超时 | 关闭即走（不等积压、不等声卡），设置提前落盘 | 关闭耗时实测约 46 ms |
| 13 | "点了个按钮没反应" | 功能未实现但按钮仍在 | **不做的功能明确说明原因**（图形字幕、视频轨道切换、镜像文件、杜比视界 Profile 5） | 相关提示的测试 |

## 5. 需求优先级是怎么定下来的

| 判据 | 含义 | 落到需求上 |
|---|---|---|
| 是否阻断使用 | 做不到就没法用 | 播放、字幕加载、坏文件不崩 → **P0** |
| 是否每天都要用 | 高频细节决定口碑 | 排序、字幕优先策略、断点续播、全屏体验 → **P1** |
| 是否有"别人都没做"的稀缺性 | 决定答辩差异化 | 免提权的文件关联、不抢占关联、中文序号排序、不打扰策略 → **P0/P1** |
| 是否只在少数场景出现 | 锦上添花 | 截图、幻灯片、右键菜单项、内置快捷键帮助 → **P2** |
| 是否说了"不做什么" | 避免半成品伤害信任 | 图形字幕、视频轨道切换 → 明确不支持并提示 |

## 6. 技术路线调研

### 6.1 四条候选路线

| 路线 | 做法 | 优点 | 缺点（对我们最致命的） |
|---|---|---|---|
| **A. 网页技术外壳**（Electron / WebView + 网页播放内核） | 用网页技术画界面，播放交给浏览器内核 | 开发快、界面好看、生态大 | 安装包与内存开销大（几百 MB 起）；浏览器内核能解码的格式与色彩处理有限；HDR 与专业字幕格式基本无法处理；"轻快"这条从一开始就做不到 |
| **B. C++ / Qt 直接调用 FFmpeg** | 传统做法，功能最强 | 性能上限最高、控制力最强 | 开发成本高、内存安全要靠人守；崩溃风险高（一个越界就是整个程序消失）；跨平台后续维护成本高 |
| **C. 外部进程方式**（自己做个界面，调用现成的 `ffmpeg.exe`） | 界面与解码分离 | 起步简单 | 每次播放都要启动外部进程并等待初始化，首帧慢、进度跳转延迟明显、进程间同步难以精确；分发还要带一个巨大的可执行文件；**本质上是"套壳"，答辩也没有技术含量** |
| **D. 现代系统级语言 + 进程内直接集成解码内核 + 轻量原生界面（本方案）** | Rust 编写，解码内核以库的形式直接编进程序，界面用轻量原生渲染 | 没有子进程与管道预热 → 启动就是快；内存安全由语言保证 → 崩溃可控；体积小、依赖少；界面与解码解耦，各层可独立测试 | 学习曲线陡；必须捆绑解码库（约 180 MB）；系统集成部分与 Windows 绑定 |

### 6.2 选型结论

**选择路线 D**，理由：

1. **"快"是产品的核心卖点之一**，只有"解码内核在进程内"才能做到毫秒级启动与关闭（对比路线 C 的子进程启动开销）。
2. **稳定性靠语言保证而不是靠纪律**：播放器要处理大量来源不明的文件，越界访问与野指针是崩溃的主因；现代系统级语言在编译期就挡住这类问题。
3. **体积可控**：界面用轻量原生渲染，不需要塞进一整个浏览器内核；最终程序本体约 14 MB。
4. **可测试**：四层结构（媒体引擎 / 系统集成 / 字幕解析 / 界面）各自独立，能用自动化测试覆盖，而不是只能靠"点一遍看看"。

### 6.3 代价与取舍（主动说明，避免被问倒）

| 代价 | 我们的处理 |
|---|---|
| 团队需要花时间掌握一门新语言 | 已沉淀 200 余项自动化测试与内部设计文档，降低后续维护成本 |
| 必须捆绑约 180 MB 的解码运行库 | 采用"绿色目录"分发；本体仅约 14 MB，运行库按需替换 |
| 目前仅 Windows | 明确标注；因为系统集成（文件关联、单实例、防休眠、深色标题栏）是产品价值的一半，跨平台"空实现"没有意义 |

## 7. 关键技术难点的调研结论（非技术表达）

| # | 现象 | 常见做法的坑 | 我们的结论 | 用户能感受到的效果 |
|---|---|---|---|---|
| 1 | 声音和画面越放越不同步 | 直接拿声卡计数当"时间标准"。但驱动只是报告"我收到了多少采样"，有的驱动一次吞掉一整秒，有的读完还继续播缓冲数据 | 用系统的单调时钟当时间标准，让声音去追画面 | 长片播放不漂移，不会出现"看着看着口型对不上" |
| 2 | 拖进度条后画面冻结 / 时间越跑越长 | 控制指令（跳转）和媒体数据排在同一条队伍里，跳转要排在几十个待处理数据后面 | **控制指令不走数据队列**，直接下发；画面数据在拥堵时可以丢弃，声音数据绝不丢弃 | 拖动能立刻响应，不会"越拖越卡" |
| 3 | 多音轨片子在播放中途切轨会卡住 | 切换轨道时，旧的"数据结束"信号可能晚于新的会话到达，把新解码器直接关掉 | 每个数据包与结束信号都带"会话编号"，编号过期的直接忽略 | 切音轨/字幕轨后画面与声音正常回来，不会"切完就黑屏" |
| 4 | 4K 素材放着放着内存爆掉 | 只按"缓存多少帧"限制，而 4K 一帧就有 30 多 MB | 所有缓存**按数据量**限制，另外再按"领先播放位置多少秒"限制 | 长时间播放内存平稳，不会越放越卡 |
| 5 | 中文外挂字幕乱码 | 默认只认 UTF-8 | 依次尝试常见编码（含 GBK / Big5 / Shift_JIS 等），按整段文本的可读性判断 | 下载来的字幕直接就能看 |
| 6 | 蓝光式片源跳转慢/黑屏 | 这类容器没有索引，只能靠大量读取定位，而读取过程会回调播放器自身，处理不当就自己把自己锁死 | 跳转时用"可中断"的读取，并把中断请求放在安全的位置取走 | 蓝光片源可以正常拖动，跳转不会永久冻结 |
| 7 | 设置默认播放器要管理员权限 | 直接写系统级的注册信息 | 只写当前用户区即可达到同样效果，且不会与其他播放器抢关联、卸载无残留 | 普通用户点一下就能设为默认 |
| 8 | 大图/幻灯片一卡一卡 | 每一帧都把整张图重新转换、重新上传给显卡 | 画面没变就不重复上传；窗口最小化时完全不处理画面；超过上限自动缩小 | 翻页顺畅，显存不会被一张图吃光 |
| 9 | HDR 画面发灰 | 直接按普通显示范围输出 | 识别元数据后按人眼感知曲线做映射（低亮度原样保留、高光柔和收敛），并允许关闭 | HDR 片子看起来"通透"，但不高亮刺眼 |
| 10 | 关窗口要等一两秒 | 关闭时还在把队列里剩下的数据处理完、还在等声卡超时 | 关闭时直接放弃积压数据、先让声卡停下来，设置提前落盘 | 点关闭立刻退出（约 46 ms） |

> 答辩讲法建议：不要讲"我们怎么实现的"，而是讲**"我们发现别人在这个地方是怎么栽的，我们换了条路，效果是这样的"**。
> 每个难点都能对应一段可演示的行为。

## 8. 差异化定位

> **一句话定位**：
> 一款为 Windows 打造的"默认播放器本该有的样子"——**不挑格式、中文优先、免安装免提权、开得快关得快、绝不打扰你**。

三条差异化支柱：

| 支柱 | 一句话 | 支撑 |
|---|---|---|
| **中文优先** | 别人把它当作"语言选项"，我们把它当作核心能力 | GBK 等 6 种编码识别、语言后缀优先匹配、中文序号自然排序、全中文界面 |
| **系统级整合 + 零权限** | 像系统自带的一样贴手，却不需要管理员 | 免安装绿色目录、一键关联 100+ 扩展名、不抢占他人关联、卸载零残留、单实例并窗、防休眠 |
| **快与稳** | 毫秒级启动与关闭，坏文件带不走程序 | 启动自有代码 6–8 ms、关闭约 46 ms、坏文件只提示不崩溃、所有缓存有上限 |

一句话对比（答辩可直接说）：

> **VLC / PotPlayer 是"功能最多的播放器"，我们做的是"最不需要你操心的那个中文用户的播放器"。**
