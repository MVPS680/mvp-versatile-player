## 一、功能总览（PPT 一页式清单）

### 播放

- 直接集成解码内核（不调用外部程序、没有等待预热）
- 硬件解码（显卡不支持时自动回退软件解码）
- HDR10 / HLG 画面不发灰；杜比视界配置信息识别与如实提示
- 播放 / 暂停 / 停止 / 精确跳转 / **单帧步进**
- **保持音高的变速播放** 0.25x–4.0x
- A–B 循环、列表循环、单曲循环、随机播放
- 音量 0–200%（带软限幅，不会爆音）、静音
- 音轨 / 字幕轨切换，音频与字幕延迟微调（±10 秒）
- 断点续播（记住每个文件看到哪）
- 截图保存为 PNG（自动放进"图片\MVP Snapshots"）
- 网络串流：`http` / `https` / `rtsp` / `rtmp` / `udp` / `rtp` / `srt` / HLS
- 文件夹递归拖入（最多 4 层）+ 自然排序 + 播放列表文件展开

### 字幕

- 内嵌字幕：SRT / ASS / SSA / MOV_TEXT / WebVTT
- 外部字幕：同目录同名自动加载，优先匹配 `.zh` / `.chs` / `.cht` 等语言后缀
- 内嵌优先 or 外部优先可切换（默认外部优先）
- **编码自动识别 6 种**：UTF-8 / UTF-16（含 BOM）/ GBK / Big5 / Shift_JIS / Windows-1252
- 字号、颜色、衬底、距底部距离可调
- 图形字幕（PGS / VobSub）无法显示时**明确提示原因**

### 图片

- PNG / JPEG / GIF / WebP / BMP / TIFF / ICO / TGA / QOI / PNM / EXR 等
- 动画 GIF / WebP / APNG 逐帧播放
- 缩放、平移、旋转、水平垂直翻转、适应窗口、100% 原图
- 幻灯片播放
- 按 EXIF 方向自动旋转（手机照片不侧躺）
- 超大图自动缩小，不会耗尽显存

### Windows 集成

- 原生"打开方式"与可选的右键菜单项
- **一键文件关联**：视频 / 音频 / 图片 / 播放列表 100 多种扩展名
- **只写当前用户区，全程不需要管理员权限**
- 不抢占其他播放器已占用的关联；取消关联零残留
- 单实例：再次双击文件并入已打开的窗口，不新开第二个
- 深色标题栏、播放时阻止屏幕与系统休眠

### 界面

- 暗色、低干扰的**纯色**界面（不做毛玻璃/半透明，画面才是主角）
- 全矢量图标，任意 DPI 清晰，不使用 emoji
- 侧边栏四页：播放列表 / 轨道 / 章节 / 媒体信息
- 性能统计面板：解码帧数、丢帧、队列深度、音频欠载、启动耗时
- 全屏时控制栏自动隐藏，鼠标一动就回来
- 全中文界面 + 内置快捷键帮助（F1）

## 二、六大亮点（每条 = 一句话卖点 + 30 秒展开 + 演示步骤 + 数据支撑）

### 亮点 1 · 像系统自带的一样贴手，却不需要管理员权限

- **一句话**：一键把自己设成默认播放器，覆盖 100 多种扩展名，**不动系统、不要密码、卸载无残留**。
- **30 秒展开**：几乎所有播放器要接管"双击用谁打开"都得提权，办公电脑上根本不给权限。我们只写当前用户自己的设置区，效果完全一样；而且**不会抢走**其他播放器已经占用的关联 —— 我们已经在一台同时装着别的播放器的真实电脑上验证过，注册、检查、注销全程通过，注销后不留任何痕迹。
- **演示步骤**：设置 → 系统集成 → 注册文件关联 → 回到桌面双击一个素材 → 打开的就是它。
- **数据支撑**：5 项真实注册表测试（默认跳过，验收时手动开启），覆盖注册 / 描述 / 注销 / 零残留 / 不抢占。

### 亮点 2 · 开得快，关得也快

- **一句话**：窗口出现前只做三件事；点关闭立刻就走，不等缓存、不等设备。
- **30 秒展开**：很多播放器启动时要初始化一堆东西才肯显示窗口。我们把"必须做的事"压到最少：读命令行、写一次单实例标记、加载一份中文字体 —— 自有代码只花 6–8 毫秒，其余时间都在等系统创建窗口和显卡驱动。关闭时同理：队列里没处理完的数据直接放弃，声卡先停下来，设置其实每 2 秒已经悄悄存过一次，所以退出只花约 46 毫秒（播放中），空窗口约 15 毫秒。
- **演示步骤**：秒表/录屏演示"双击图标 → 窗口出现"和"点击关闭 → 图标从任务栏消失"。
- **数据支撑**：启动自有代码 6–8 ms（调试构建）、关闭约 46 ms（发布构建，播放中）、空窗口约 15 ms、程序本体约 14 MB。

### 亮点 3 · 中文用户的两个老毛病，我们正面解决

- **一句话**：GBK 字幕不乱码，剧集顺序不再乱。
- **30 秒展开**：国内下载的字幕大多是 GBK 编码，很多播放器默认只认 UTF-8，打开就是一堆方块。我们自动识别 6 种常见编码，并且**优先挑中文语言后缀**的字幕文件。第二个细节更少人注意：文件名排序如果按字符来，"第10集"会跑到"第2集"前面去，我们做了自然排序，播种式的看剧不用再手动排。
- **演示步骤**：打开同目录带 GBK 外挂字幕的视频 → 字幕正常显示；打开剧集文件夹 → 侧边栏列表顺序为 第1、第2 …… 第10。
- **数据支撑**：字幕解析测试 53 项（含 GBK 中文用例）；播放列表排序单元测试。

### 亮点 4 · 不支持的东西，我们说出来（不糊弄用户）

- **一句话**：不黑屏、不刷错误、不给你一个点了没反应的按钮。
- **30 秒展开**：光盘镜像是"容器里的容器"，直接丢给解码器只会刷一屏错误 —— 我们提示用户先装载镜像；PGS 这类图形字幕本质是图片，需要文字识别才能显示 —— 我们明确告诉用户这条轨道显示不了；杜比视界 Profile 5 我们无法正确还原 —— 我们如实写出来，而不是装作正常播放。**把边界讲清楚，比假装全能更值得信任**，这也是评委最想看到的产品态度。
- **演示步骤**：打开一个 ISO 镜像 → 弹出明确提示；打开带 PGS 字幕的素材 → 轨道页写明原因；打开杜比视界素材 → 信息页显示 Profile / Level / 单层双层。
- **数据支撑**：独立的异常处理测试（损坏文件不崩溃）；"解码无输出"守护：持续投喂却长时间没有画面时，12 秒内报错并停止空转。

### 亮点 5 · HDR 不发灰，杜比视界信息透明

- **一句话**：HDR 片子不再像蒙了一层雾，还能告诉你它到底是什么规格。
- **30 秒展开**：HDR 影片按更高的亮度标准制作，普通屏幕直接放会整幅发灰。我们识别 HDR 元数据并做画面映射：亮度较低的部分原样保留，只把高光柔和地收敛 —— 观感是"通透"，而不是"刺眼"。不需要这个效果的用户可以在设置里一键关掉。杜比视界影片我们播放它兼容的基底层，并把 Profile / Level / 单层双层等信息显示在媒体信息页。
- **演示步骤**：同一段 HDR 素材，切换"色调映射 开 / 关"做对比（建议提前录制对比短视频，见"兜底方案"）。
- **数据支撑**：HDR 与杜比视界相关的可选用例（真实样本体积过大不入库，验收时另行提供）。

### 亮点 6 · 敢改、也守得住：200 余项自动化测试

- **一句话**：改代码不怕改坏，因为坏没坏由测试说了算。
- **30 秒展开**：播放器最怕"修好一个地方、捅坏另一个地方"。我们把测试分成了几层：16 项端到端真实解码播放测试（真的去解码素材，验证画面非空、时间戳正确、跳转落点正确、损坏文件不崩溃）、11 项界面行为测试（按真实使用顺序驱动整个播放流程，包括"打开文件前就先把字幕关掉"这种曾经让画面永远卡在准备中的坑）、59 项引擎单元测试、53 项字幕解析测试、31 项 Windows 集成测试、46 项界面与命令行测试。
- **演示步骤**：现场跑一次全量测试（或展示测试报告截图），强调"绿色"来自真实解码而不是模拟。
- **数据支撑**：见"关键数据卡"。

## 五、答辩问答准备（高频 12 问）

**Q1：市面上已经有 VLC、PotPlayer 了，你们凭什么再做一遍？**
A：我们不比"功能总量"。我们的差异集中在三件事：① 中文素材的细节（GBK 字幕、语言后缀、中文序号排序）；② 免安装 + 免管理员 + 不抢占他人关联；③ 启动与关闭的毫秒级速度。用一句话说：VLC 是"功能最多的播放器"，我们做的是"最不需要操心的那个中文播放器"。

**Q2：为什么不基于 VLC 或 mpv 套一层界面？那样不是更快？**
A：套壳能很快做出"能用"的东西，但做不到我们最看重的三点：首帧速度、界面与系统整合的完整控制、体积。而且从技术含量上说，套壳等于把核心能力交给别人 —— 我们在解码、时钟、跳转这些问题上做的判断才是这个项目真正的价值。

**Q3：为什么只支持 Windows？**
A：产品价值的一半是系统整合（文件关联、单实例、深色标题栏、防休眠），这些东西在其他平台要么完全不同、要么不存在。做"能编译但功能是空的"跨平台版本对用户没有意义。我们选择把一个平台做透。

**Q4：捆绑了 180 MB 的解码运行库，还算"轻量"吗？**
A：程序本体约 14 MB，界面与逻辑都是自己的；180 MB 是解码能力的必要成本，因为格式支持必须靠它。我们用绿色目录分发，不需要安装，直接拷走就能用。

**Q5：许可上会不会有风险？**
A：本项目以 GPL-3.0-or-later 发布，内置的解码库也是 GPL 构建，两者一致，是合规的组合。如果未来要换成更宽松的许可，需要替换解码库中带 GPL 的部分，这是我们已知的约束。

**Q6：杜比视界不支持增强层，算不算没做完？**
A：杜比视界的完整还原需要专用渲染路径。我们的做法是：播放兼容基底层（画面仍是 HDR10 效果），并把 Profile / Level 等信息如实显示；无法正确还原的 Profile 会明确提示。**我们宁可说清楚，也不假装正常播放**。

**Q7：HDR 色调映射好像很慢？**
A：目前是处理器上的近似实现，这是已知的最大性能瓶颈，也是我们下一步的首选项（改用显卡着色器）。我们已经把这条写进"已知边界"，而不是藏起来。

**Q8：你们怎么保证改代码不引入回归？**
A：200 余项自动化测试分六层，其中包含真的去解码素材的端到端测试，以及按真实使用顺序驱动整个播放流程的界面行为测试。核心路径（打开、跳转、切轨、关闭）都有覆盖。

**Q9：有没有做用户调研？**
A：有。方法是用同一批素材实测主流播放器，逐项记录卡在第几步，形成"痛点 → 对策 → 可验证功能点"的对照表；同时团队成员本身就是目标用户（看片、网课、整理素材）。样本规模我们如实说明，不夸大。

**Q10：截图、逐帧、变速这些是不是很常见？**
A：单项功能不稀奇，但它们是同一个用户场景里的连续动作：看网课时暂停 → 逐帧找到关键画面 → 截图 → 变速继续听。我们把这三件事放在同一个界面里，不用切换软件。

**Q11：为什么不做视频轨道切换和图形字幕？**
A：多视频流和图形字幕在真实素材里出现频率很低，而做半成品会伤害信任。我们的原则是：**做不到的能力，明确告诉用户原因**，而不是给出一个点了没反应的按钮。

**Q12：这个项目最大的技术难点是什么？**
A：两个。一是音视频同步：声卡报告的数字并不可靠，我们改用系统时钟做时间标准，长片播放不漂移。二是跳转的可靠性：控制指令不能和数据排同一条队，而且必须能识别"过期的会话信号"，否则切轨或连续拖动后画面会永久冻结 —— 这两个问题都在真实素材上复现过并修复了。
